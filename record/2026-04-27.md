## 1. LLM推理阶段

LLM 推理分为两个阶段：

- **Prefill 阶段**：处理输入 prompt，生成第一个 token，同时将 KV Cache 写入显存
- **Decode 阶段**：逐 token 生成，每次只处理一个新 token，需要读取历史 KV Cache

其中，Prefill阶段可以通过casual mask一次性并行计算所有token，同时进行KVCache，计算密度较高，存在计算瓶颈。

Decoder阶段对显存带宽更加敏感，因为每次只生成一个token，计算压力较小。但每次都要读取KVCache，所以存在显存带宽瓶颈。

## 2. Paged-Attention

KVCache存在请求长度不同、内存碎片化的问题。

1. 请求（request）可以类比为操作系统中的一个进程，每个请求对应一段独立增长的 KV cache。  
2. 逻辑内存（logical KV blocks）可以类比为虚拟内存中的页（virtual pages），每个 block 大小固定（例如 vLLM 默认一个 block 可存储 16 个 token 的 K/V），用于表示该请求在“逻辑上连续”的 KV 序列。  
3. 块表（block table）类似于页表（page table），用于维护逻辑 block 到物理 block 的映射关系。  \#filled表示该Block被填充了多少个token。
4. 物理内存（physical KV blocks）可以类比为物理页框（physical page frames），实际分配在 GPU 显存中，不同逻辑 block 在物理上可以是非连续存储的。  
5. 在进行 attention 计算时，模型会根据 block table 将逻辑上连续的 KV 序列映射到物理上分散的 KV blocks，从而实现高效的 KV cache 管理与访问。

![](pagedAttn.png)

每个request都有状态记录当前有多少token，第 $t$ 步时需要访问0, 1, 2, ..., $t-1$ token。
假设：
- block size = B（例如 16 tokens）
- 当前要访问第 t 个 token

$$block_{id}=⌊B​⌋,offset=t \space mod \space B$$
再通过Block table：
$$physical\_block = block\_table[block_{id}]$$
最终地址：
$$addr = physical\_block + offset$$
