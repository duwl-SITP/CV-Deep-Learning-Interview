## 1. 什么是KVCache?

在基于 Transformer 架构的模型中，生成文本是一个自回归（Autoregressive）过程。每生成一个新的 Token（字符或词组），模型都需要将当前 Token 与之前所有的 Token 进行注意力计算（Attention Mechanism）。

### 冗余计算问题

如果不使用 KVCache，每生成第 $n$ 个 Token，模型都需要重新计算前 $n-1$ 个 Token 的 **Key (K)** 和 **Value (V)** 矩阵。由于前序 Token 的内容在生成过程中是不变的，这种重复计算会导致计算量随序列长度呈平方级增长（$O(n^2)$），极大地浪费算力资源。

### KVCache 的解决方案

KVCache 的机制是在计算第 $i$ 个 Token 时，将其对应的 $K_i$ 和 $V_i$ 向量存储在内存（通常是 GPU 显存）中。当生成第 $i+1$ 个 Token 时：

1. 模型仅需计算第 $i+1$ 个 Token 的 $Q_{i+1}, K_{i+1}, V_{i+1}$。
    
2. 从缓存中读取前 $i$ 个 Token 的 $K$ 和 $V$ 矩阵。
    
3. 将 $K_{i+1}$ 与之前的 $K$ 拼接，完成注意力权重计算。
    
4. 将计算结果与拼接后的 $V$ 矩阵进行加权求和。

## 2. KVCache存在什么问题？ 

- **静态预分配导致的资源浪费**：传统方案通常依据模型允许的最大上下文长度（Max Sequence Length）预先划定显存空间。当实际生成的 Token 序列远小于预设上限时，大量已分配的显存处于闲置状态，显著降低了系统的并发处理能力。
    
- **长序列溢出风险**：随着对话轮次增加或生成内容的增长，Token 序列总量可能突破预设的显存容量上限。由于 KVCache 必须完整保留历史键值对以维持推理连贯性，一旦发生溢出，系统将面临强制截断上下文或触发显存溢出（OOM）异常的风险。
    
- **内存布局碎片化**：不同请求的 Token 长度存在显著差异且呈动态增长态势，导致显存空间被划分为大小不一的非连续块。这种动态需求与静态分配机制之间的不匹配，造成了严重的内存碎片化问题，进一步限制了显存的有效利用率。
